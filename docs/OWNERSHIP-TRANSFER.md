## Design choice and responsibility

Two paths are plausible. Moving the source and copying Frame into the existing organization tap preserves the established organization publishing system and the personal compatibility tap. Renaming/replacing the organization tap to make room for a direct personal-tap transfer would disrupt Key/xkcdpass and their migration history. Use the first path.

The source repository owns code, tests, app identity, signed release bytes, checksums, tags, and release notes. The organization tap owns Frame cask rendering, downloaded-release validation, Homebrew tests, proposal branches, and update PRs. The personal tap owns only the eventual migration stub and rejection of obsolete publication requests. A maintainer coordinates their order and approves sensitive integration changes. Keep publication manually dispatched; source CI must not receive a cross-repository write credential or merge generated tap PRs automatically.

The organization verifier currently requires GitHub's `immutable=true` specifically for xkcdpass. Frame's existing `v3.2.0` does not meet that condition, although its two assets have API SHA-256 digests. Do not copy that requirement blindly or replace old assets to make a migration pass. For the initial migration, explicitly qualify the existing published state and recorded hashes under the chosen Frame contract. If organization policy instead requires enforced immutable releases, obtain approval and qualify a future genuine release before migrating users; no version or release setting changes are part of this pass.

## Staged execution and gates

1. **Qualify and review CI first.** Review the isolated Frame CI branch and hosted success/failure evidence. Merge only through the repository's review process. A maintainer can separately configure `Required checks` as a protected status once the PR check is qualified. This plan does not grant bypasses or change protections. Record the exact source/tap heads, releases, asset SHA-256 values, app signing requirement, enabled workflows, app selections, and operator permissions before any transfer. Freeze new source releases and tap publication during the cutover; existing installations must continue using the verified historical downloads until the complete destination route is qualified.

2. **Prepare organization-tap support as separate work.** Add a Frame package choice, a Frame-specific release verifier, cask update handling, tests, and `Casks/frame.rb` in `tvr-works/homebrew-tap`. Reuse its verify/propose split; do not send Frame through the Key archive assumptions. Verify a published stable tag, expected release state/canonical owner, exactly `Frame-v<version>.zip` plus `checksums.txt`, API asset digests and the manifest, universal app/CLI layout, and matching version metadata. Require the existing bundle identifier, supported macOS floor, executable paths, and valid distribution signatures. Prepare against the current trusted source and switch to the canonical organization source after transfer, or hold the change until that canonical source exists. Do not merge a cask with a nonexistent download URL. Keep the personal Frame cask available throughout this stage.

3. **Transfer the existing Frame source repository.** The operator must have source admin rights, permission to create an organization repository, and an available destination name without a conflicting fork. Recheck these prerequisites rather than relying on this snapshot. Use GitHub's repository transfer operation, retain public visibility, and verify repository identity, history, tags, releases, open PRs/issues, assets, and permissions afterward. Keep the old namespace unused. Test old and new clone URLs and every currently supported release URL, including a checksum comparison with the pre-transfer inventory, before changing user instructions.

4. **Update active source references.** In a reviewed source PR, change the source repository URL and `FRAME_REPO_SLUG` to `tvr-works/frame`. Prepare `FRAME_HOMEBREW_TAP=tvr-works/homebrew-tap` and its shell dispatch expectations, but activate that route only after destination Frame support passes stage 6. Update README, release docs, and remaining active owner references in step with those gates. Leave product names, bundle IDs, config paths, stable versions, and existing release assets unchanged. Update developer remotes, for example `git remote set-url origin https://github.com/tvr-works/frame.git`, only after the canonical repository is verified. Local clones using the redirect remain temporary compatibility paths.

5. **Qualify integrations under organization ownership.** Recheck Actions policies, approvals, effective token permissions, secrets metadata, app selection, and required reviews. The verified all-repository Blacksmith installation can cover the transferred repository, but it still needs a real qualified run. Its documented labels include `blacksmith-2vcpu-ubuntu-2404` and `blacksmith-6vcpu-macos-26`. Switch the portable job only after repository eligibility is confirmed. Keep macOS execution for Swift/AppKit and packaging; qualify the pinned Xcode path on the Blacksmith macOS image before switching those jobs. Retain GitHub-hosted macOS until that succeeds. No billing change or installation expansion is implied. [Blacksmith quickstart and eligibility](https://docs.blacksmith.sh/introduction/quickstart), [runner catalog](https://docs.blacksmith.sh/blacksmith-runners/overview).

6. **Integrate the destination cask, then move existing brew users.** Complete the organization tap's Frame checks and merge its current-version cask first. It can initially reference the already published release; do not invent a version bump to move ownership. Next integrate Frame's organization-tap dispatch and contract-test changes, so future updates cannot target an unsupported destination. Once installation/upgrade continuity is proven, change the personal tap in its own PR: remove `Casks/frame.rb`, add `"frame": "tvr-works/tap"` to its existing `tap_migrations.json`, add migration tests, and make its old Frame publication path fail before contacting GitHub. Preserve the existing Key and xkcdpass migrations. Never delete the compatibility tap while clients still depend on it. Homebrew reads tap migration metadata to resolve packages; the installed receipt and legacy-update path require a real sandboxed qualification, not just a JSON assertion. [Homebrew tap migration implementation](https://github.com/Homebrew/brew/blob/master/Library/Homebrew/tap.rb), [cask resolution](https://docs.brew.sh/rubydoc/Cask/CaskLoader.html).

7. **Prove the complete route before the next release.** In disposable macOS environments, verify a fresh organization install and an existing personal-tap installation through `brew update`, `brew tap tvr-works/tap`, and `brew upgrade --cask tvr-works/tap/frame`. Check that the receipt points to the destination tap, there is one app and one CLI link, versions match, configuration remains readable, and no uninstall/data deletion is required. Test a later strictly newer version when one is genuinely released; same-version migration alone does not prove future upgrades. Also exercise the old fully qualified token and an interrupted migration. After user consent for device testing, verify Accessibility permission and login-item continuity with the same signing identity. This task does none of those live installs or permission changes.

8. **Publish through the original boundary.** Once both source and tap changes are integrated and independently qualified, the source maintainer creates the next signed release normally. At the separate Homebrew checkpoint, dispatch only the organization tap's `publish-package.yml` with `package=frame` and that published version. The tap validates, renders, checks, and proposes the update. Workflow-generated PR approval and review remain maintainer actions; never broaden the source token to avoid that boundary.

## User prerequisites and recovery limits

Execution needs explicit approval to transfer the source, reviewed changes in both taps, organization repository-creation rights, effective Actions/app permissions, a maintainer able to approve workflow runs and merge tap PRs, and authorized access to the existing Developer ID signing team. GitHub ownership and Apple publisher ownership are separate. If the business requires a different Apple team, stop and qualify that identity transition separately; preserving the bundle ID alone does not guarantee existing Accessibility grants survive a team change.

Before the personal migration entry is merged, a destination problem can leave users on the still-maintained personal cask. After migration begins, some clients will have destination receipts and others legacy receipts; removing the forwarding entry or deleting the old tap does not reverse clients already migrated. Prefer forward fixes in the organization cask, retain compatibility metadata, and document any manual recovery. A GitHub transfer-back is subject to ownership/name permissions and is not an asset or client-receipt rollback. Never move an existing release tag, replace published ZIPs/checksums, or republish a historical version as recovery. Pause future publication and issue a new patch release if distribution bytes need correction.

## Notarization is a separate qualification

The inspected build script validates code signatures but contains only a TODO for notarization/stapling. The installed release's signing flags do not show Hardened Runtime. The new CI intentionally creates ad-hoc-signed packages, which are not distribution-signed or notarized. No Apple submission or Gatekeeper success is claimed here.

A separate distribution change must qualify Hardened Runtime for both app and CLI, secure timestamps, required entitlements, nested code signatures, `notarytool` submission and logs, stapling where supported, and online/offline Gatekeeper checks on quarantined downloads. Packaging/checksums must be finalized after any stapling so published bytes remain immutable. Do not assume the app's ticket covers a separately distributed CLI. The personal cask currently removes quarantine in postflight; that is not notarization, and its future handling requires an explicit reviewed distribution decision rather than silently copying or expanding the workaround. No signing secret or notary credential belongs in ordinary CI. [Apple's notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).
